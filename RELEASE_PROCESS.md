# Protected SPOT OS release procedure

This document prepares the reviewed OS release tuples below, including 0.1.7 stable. Tests and pull requests do not sign or
publish a release. A human must review and merge the signer changes, approve
the exact private source commit and explicitly dispatch the existing workflow.
Never overwrite an existing tag, ZIP, manifest or signature.

## Exact compatibility policy

| OS version | Tag | Sequence | Minimum OS | Maximum OS | Minimum app | Channel | Reboot |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0.1.4 | os-v0.1.4 | 104 | 0.1.3 | 0.1.3 | 0.28.12 | prerelease | false |
| 0.1.5 | os-v0.1.5 | 105 | 0.1.4 | 0.1.4 | 0.28.13 | prerelease | false |
| 0.1.6 | os-v0.1.6 | 106 | 0.1.4 | 0.1.4 | 0.28.13 | prerelease | false |
| 0.1.7 | os-v0.1.7 | 107 | 0.1.6 | 0.1.6 | 0.28.13 | stable | false |

Historical rows remain available for verification; they are not permission to
replace published releases. OS 0.1.5 and 0.1.6 are **not** allowed predecessors
of this 0.1.6 candidate. The signer and anonymous verifier share this allowlist.
The app minimum, OS range and reboot flag are generated by the signer, not
operator-controlled workflow inputs. For stable 0.1.7 both the Environment variable
`SPOT_OS_STABLE_RELEASES_ENABLED=true` and explicit workflow input
`hardware_approved=true` are required. Neither is set by tests or by this PR.
Historical prereleases remain verifiable without these gates.

## Before dispatch (operator actions, not performed by tests)

1. Review and merge the public signer PR. Select `main` in this repository.
2. Read the **current** `main` SHA of private `Koco-008/SPOT`. Use all 40 lower-case
   hexadecimal characters. A feature branch SHA or a historical main SHA is
   insufficient, even if it has successful CI.
3. Wait for `.github/workflows/os-candidate.yml` at exactly that SHA: event
   `push`, branch `main`, completed success, first attempt only, with successful
   `verified-os-candidate` job. Failed, rerun, manual and PR runs are rejected.
   If that run failed, fix the private source and obtain a fresh main push;
   do not substitute a manual dispatch or broaden the signer checks.
4. Check the private staging prerelease `ci-os-candidate-<SHA>` contains exactly
   `spot-os-0.1.6.zip` and `proof.json`. The proof's source, version, size and
   SHA256 must match the ZIP and the job log's single
   `SPOT_OS_CANDIDATE_SHA256=...` line. Its internal `PACKAGE.json` must cover
   every runtime member and its embedded OS key must match the existing identity.
   Downloaded private code is inspected as data and never executed by the signer.
5. In Environment **`spot-os-release`**, set the nonsecret variable
   **`SPOT_OS_APPROVED_COMMIT`** to that same full current private main SHA.
   Retain the existing required reviewer, main branch restriction and disabled
   admin bypass. Do not change secrets or rotate keys. Keep existing
   `SPOT_OS_SIGNING_ENABLED=true` and independently checked
   `SPOT_OS_PUBLIC_KEY_SHA256`:
   `b142b246c22fd6f56f4207b86bbd5dcef09b122d228af81c0c51130d4309f907`.
   The existing source-read credential must be able to read branch metadata,
   Actions job logs and private release assets; do not expose its value.
6. Confirm public `os-v0.1.6` does not exist. Dispatch **Protected SPOT OS
   signing**, `.github/workflows/release-os.yml`, on public `main` with:

   ```text
   source_commit: <FULL_CURRENT_PRIVATE_MAIN_SHA>
   tag: os-v0.1.6
   sequence: 106
   previous_os: 0.1.4
   channel: prerelease
   ```

7. Review the exact source and workflow run at the existing Environment gate
   before approving. The signer checks actual private main before and after
   fetching/verifying the candidate. If main advances during that operation,
   it fails closed: review the new SHA and its new push CI rather than reusing
   the old approval. This is an API snapshot check, not a lock on private main;
   avoid advancing main during the controlled release window.

The existing independent OS Ed25519 key remains exclusively in the protected
signing job. App signing uses a different identity. No device credentials are
needed for public updates.

## After explicitly approved publication

The unchanged workflow publishes exactly four files as a prerelease:
`spot-os-0.1.6.zip`, `os-update.json`, `os-update.json.sig`, `SHA256SUMS.txt`.
It compares downloaded bytes and checksums, then downloads again anonymously
and verifies the Ed25519 signature, pinned key, exact compatibility/source
metadata, ZIP digest and all member hashes.

Independent verification (replace the SHA with the approved source):

```sh
python signer/verify_public.py --tag os-v0.1.6 --commit FULL_CURRENT_PRIVATE_MAIN_SHA --sequence 106 --previous 0.1.4 --fingerprint b142b246c22fd6f56f4207b86bbd5dcef09b122d228af81c0c51130d4309f907
```

OS 0.1.6 requires the signature-bound **one-time administrative preparation**
documented in the private source's `spot_os/MIGRATION_014_016.md` for the old
0.1.4 updater sandbox. The signed manifest's compatible range does not imply
that an unprepared 0.1.4 installation can perform this OTA automatically.
Keep app 0.28.13, the running driver and user data unchanged. Real Pi OTA and
rollback acceptance remain a separate task; signer CI does not prove them.

## Review tests (no release, no production credentials)

```sh
python -m py_compile signer/sign_candidate.py signer/verify_public.py
python -m unittest discover -s signer -p 'test_*.py' -v
```

Tests retain the existing ephemeral test-identity pattern; no productive key is
created or accessed. CI additionally verifies the historical public 0.1.4
release anonymously. The release workflow itself and its Environment binding
are unchanged by the 0.1.6 signer preparation.

## OS 0.1.7 stable (not dispatched by this change)

The operator tested 0.1.6; this does not approve 0.1.7. Keep the stable gate
closed until the operator accepts the exact new build on a separate test SD
under an explicitly agreed trusted test procedure. Record source SHA, package
hash, platform/kernel, outcomes and approval. An unsigned local build is not an
official OTA release. See private spot_os/OTA_TEST_017.md. Green CI alone must
not imply hardware approval.

After review/merge of BOTH PRs, obtain the actual private main SHA and its
successful first-attempt push-main os-candidate.yml run. The filename is now
derived from spot_os/VERSION. Check the two staging assets/proof and immutable
CI-log digest as above. A PR merge-test or feature SHA is not acceptable.

Only the operator may then set SPOT_OS_APPROVED_COMMIT to that SHA and
SPOT_OS_STABLE_RELEASES_ENABLED=true in spot-os-release. Do not change the
existing key/fingerprint, credentials, reviewers or main-only branch policy.
Dispatch release-os.yml on the PUBLIC main branch with:

```text
source_commit: <FULL_CURRENT_PRIVATE_MAIN_SHA_WITH_SUCCESSFUL_PUSH_CI>
tag: os-v0.1.7
sequence: 107
previous_os: 0.1.6
channel: stable
hardware_approved: true
```

No approval exists for OS0.1.4/0.1.5 as predecessors, prerelease017, reboot=true
or an app minimum other than 0.28.13. Both stable gates are mandatory. They
cannot turn historical prereleases into stable releases. The protected
Environment review remains the final operator boundary. Current main is checked
before and after candidate inspection; avoid advancing it during publication.
This preparation performs no merge, tag creation, Environment write or signing.

The workflow uses --prerelease=false for the signed stable channel and retains
--prerelease for older channels. Anonymous post-verification additionally reads
GitHub metadata and requires tag/draft/prerelease flags to match the signed
manifest. Signature, independent OS key, source SHA, compatibility, hashes and
all runtime members remain checked. No private history is published.

```sh
python signer/verify_public.py --tag os-v0.1.7 --commit FULL_APPROVED_PRIVATE_MAIN_SHA --sequence 107 --previous 0.1.6 --fingerprint b142b246c22fd6f56f4207b86bbd5dcef09b122d228af81c0c51130d4309f907
```

After separate approval, the healthy installed 0.1.6 discovers this stable
release without enabling prereleases. Normal touch OTA requires no 0.1.4 bridge
or Pi reboot. Its hardware acceptance remains separate from signer CI.
